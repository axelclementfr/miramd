# Internationalisation (i18n)

L'interface de MiraMD est traduite en 8 langues. Le mécanisme repose sur un store [Svelte](../01-decouverte/glossaire.md#svelte) dérivé qui sert de fonction de traduction réactive.

## Vue utilisateur

**Langues disponibles** :

- Français (`fr`)
- English (`en`)
- Español (`es`)
- Deutsch (`de`)
- Italiano (`it`)
- Português (`pt`)
- 日本語 (`ja`)
- 中文 (`zh`)

**Comment changer de langue.**

- Ouvrir les [préférences](preferences.md) (`Ctrl+,`).
- Aller dans la section **Général**.
- Choisir la langue dans la liste déroulante.
- Tous les libellés de l'interface se mettent à jour immédiatement, sans rechargement de l'application.

**Périmètre traduit.** Sont traduits :

- Les libellés de tous les boutons, menus, onglets de réglages.
- Les titres et messages des dialogues (sauvegarder / discard / annuler, erreurs).
- Les textes vides (cf. "aucun résultat", "ouvrir un dossier").
- Les noms des sections du panneau de préférences.

**Hors périmètre** :

- Le contenu Markdown que tu édites — c'est tes documents, ils restent dans la langue dans laquelle tu les écris.
- Les noms de thèmes ("Light", "Dark", "Graphite"...) — gardés tels quels.
- Les messages d'erreur Rust côté backend — généralement en anglais (logs internes).

## Implémentation

Le mécanisme est minimaliste et tient en deux fichiers principaux.

**Composants Svelte concernés** :

- `src/lib/components/settings/GeneralSection.svelte` — affiche le `<select>` de langue, écrit dans `preferences.language`.
- `src/routes/+page.svelte` — au boot et à chaque changement de la préférence `language`, appelle `setLanguage(p.language)`.
- **Tous les composants qui affichent du texte traduit** suivent le même pattern : `import { t, type TranslationKey } from '$lib/i18n/index'`, puis subscribe via `onMount` :
  ```ts
  let tr: (key: TranslationKey) => string = $state((k) => k);
  unsubs.push(t.subscribe((fn) => (tr = fn)));
  ```
  Et utilisent `{tr('save_btn')}` dans le template.

**Services / fichiers concernés** :

- `src/lib/i18n/index.ts` — le cœur du système. Trois exports :
  - `currentLang` : un `writable<string>` (default `'fr'`).
  - `t` : un `derived` de `currentLang` qui retourne **une fonction de traduction**. Cette fonction prend une `TranslationKey` et retourne la string traduite, avec **fallback sur l'anglais** si la clé manque dans la langue active, et fallback sur la clé brute si la clé manque aussi en anglais.
  - `setLanguage(lang)` : alias pour `currentLang.set(lang)`.
- `src/lib/i18n/locales/` — un fichier par langue (`fr.ts`, `en.ts`, `es.ts`, ...). Chacun exporte un objet `Record<string, string>`. Le fichier `fr.ts` sert de référence pour le type `TranslationKey` (toutes les clés doivent y figurer).

**Pourquoi un `derived` plutôt qu'une simple fonction** ? Pour la [réactivité](../01-decouverte/glossaire.md#réactivité). Quand `currentLang` change, le `derived` recalcule et tous les composants subscribés re-rendent automatiquement. Pas besoin de notifier manuellement.

**Backend Rust impliqué** : aucun. La langue est une préférence comme une autre, persistée dans `preferences.json` au champ `language`. Aucune commande [IPC](../01-decouverte/glossaire.md#ipc) dédiée à l'internationalisation. Les libellés Rust internes (logs, erreurs) restent en anglais.

**Stores impactés** :

- `currentLang` — store dédié à la langue active.
- `preferences.language` — la préférence persistée. Synchronisée vers `currentLang` au boot et à chaque changement utilisateur.
- `t` — store dérivé qui expose la fonction de traduction.

**Comment fonctionne le fallback** :

```ts
export const t = derived(currentLang, ($lang) => {
  const dict = getDict($lang);  // dictionnaire de la langue, ou anglais si absent
  const en = translations['en'];
  return (key) => dict[key] || en[key] || key;
});
```

Si une clé manque dans `fr.ts` mais existe dans `en.ts`, l'utilisateur voit la version anglaise. Si elle manque aussi en anglais, il voit la clé brute (par exemple `"unsaved_close"`). Cette stratégie évite les écrans cassés en cas de traduction incomplète.

## Pièges connus

Aucun piège connu actuellement. Le mécanisme est simple et fiable. Quelques notes pour les contributeurs :

- **Synchronisation des dictionnaires** : ajouter une clé dans `fr.ts` impose en théorie de l'ajouter dans les 7 autres `.ts` pour ne pas tomber sur le fallback anglais. Aucune validation automatique ne le vérifie pour l'instant — un test pourrait être ajouté.
- **Pas de pluralisation gérée** : la fonction `t` retourne une string brute, pas de logique singulier/pluriel. Pour `"1 match"` vs `"3 matches"`, le code doit faire le branchement à la main (cf. `SearchPane.svelte` qui utilise deux clés `match_single` / `matches`).
- **Pas d'interpolation** : pas de `{{ name }}` dans les templates. Si tu as besoin d'inclure une valeur dans un texte, tu fais la concaténation côté JS.
- **Subscribe + onMount** : tous les composants qui utilisent `tr` doivent **subscribe explicitement** dans `onMount` et stocker la fonction dans un `$state` local. Sinon, le composant ne re-render pas quand la langue change. Il existe un risque d'oubli si on copie-colle un composant.
